# Working in Batten

Batten is an application SDK in the Novirhyza family. Start with
`docs/helix/README.md`, then read the product vision and intent record.

- Read `.helix.yml` and engage the installed HELIX skill for governed work.
  Resolve graph, templates, prompts, and voice from the installed plugin; keep
  project artifacts under `docs/helix/` in the matching activity. Do not vendor
  the methodology catalog.
- Read governing upstream artifacts before authoring downstream documents.
  Preserve artifact IDs, frontmatter, and deliberate `ddx.links` traceability.
- The accepted name is Batten. The user's stated family spelling is Novirhyza;
  package scopes and registry identifiers are undecided.
- Capture incoming requirements with their source. Distinguish user decisions,
  research observations, assumptions, proposals, and unknowns. Never turn a
  sibling project's behavior or a catalog default into a Batten requirement.
- The bootstrap is ready for requirements intake. Do not invent a PRD,
  implementation plan, technology stack, hosting target, or compatibility promise
  merely to populate directories.
- The user called this a cleanroom effort based on UMF, Tether, Weft, and Arras.
  Record source provenance. Resolve the intended reuse and compatibility boundary
  before importing implementation, tests, dependencies, or repository history.
- Preserve meaning when modeling or translating data. Make unsupported meaning
  and information loss explicit; qualify support claims with versions, subset,
  and evidence. This is inherited modeling context, not blanket Batten support.
- Handwritten source is expected; the modularity-and-encapsulation baseline
  applies. Design owns the concrete boundaries and verification strategy.
- Keep credentials and private/customer data out of repository content. Use
  fabricated examples. License, distribution, and publication decisions remain
  open until provided by the owner.
